# Releasing the Android client

This is how an installable, connectable APK is produced. The `client` workflow
runs on every push: it builds the native `libbox.aar` from the pinned commit,
applies the real Android identity, and uploads a **signed release** APK. It
refuses to upload anything else — if the release configuration below is missing
or malformed, the Android job fails and names every missing value instead of
publishing an APK nobody can update. The `client-release` workflow runs the same
chain for a specific version or tag, plus an optional GitHub release.

> **Setting this up for the first time? Read
> [GitHub configuration](#github-configuration-required-for-artifacts) first.**
> Until the four secrets and two variables exist, every build that touches the
> client fails the Android job — deliberately.

## What the release build guarantees

`apps/client/tool/build-release-android.sh` refuses to produce an artifact
unless all of the following hold:

| Requirement | Why |
|---|---|
| `STRICT_ENV=production` | unsigned config bundles are rejected instead of silently trusted |
| `STRICT_CONTROLLER_URL` starts with `https://` | credentials never travel over cleartext |
| `STRICT_SIGNING_PUBLIC_KEY` is set | the client verifies the controller's Ed25519 signature; a missing key is a hard failure |
| `libbox.aar` exists | without the native engine the app installs but cannot open a VPN session. Built automatically from the sha in `apps/client/libbox.ref` |
| A real keystore is supplied | the APK is re-signed, so future builds can update it in place |

### Android identity

`apps/client/android/` is generated by `flutter create` on every clean checkout,
so the installed package id, code namespace and launcher label are applied by
`apps/client/tool/configure-android-host.sh` rather than edited by hand. Defaults:
`com.strictproxy.client` and the label `StrictProxy`; override them with
`STRICT_ANDROID_APP_ID` and `STRICT_ANDROID_APP_LABEL`. Keep the id stable after
the first release — a new id installs as a different app instead of updating.

## GitHub configuration (required for artifacts)

Every build that touches `apps/client/**` produces an APK, and that APK is
signed. It needs six repository values, set under **Settings → Secrets and
variables → Actions** (one tab each), or with `gh` as shown below. GitHub never
shows a secret again after it is saved, so keep the keystore locally.

Two more values are optional: without them the APK is still built, signed and
attached to a GitHub release, but it is not published to the controller, so
installed apps are never offered it as an update (the run prints a warning).

| Name | Kind | What it is | Where it comes from |
|---|---|---|---|
| `ANDROID_KEYSTORE_BASE64` | secret | the release keystore, base64-encoded | `base64 -w0 upload.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | secret | keystore password | the password you chose |
| `ANDROID_KEY_ALIAS` | secret | key alias inside the keystore | `upload` if you followed the keystore step |
| `ANDROID_KEY_PASSWORD` | secret | key password (optional if equal to the keystore one) | the password you chose |
| `CLIENT_CONTROLLER_URL` | variable | public HTTPS URL compiled into the app | your deployment, e.g. `https://api.example.com` |
| `CLIENT_SIGNING_PUBLIC_KEY` | variable | base64 of the controller's 32-byte Ed25519 public key (not the APK keystore) | derived from `signing-key.pem` or `SIGNING_PRIVATE_KEY_PEM` |
| `CLIENT_PUBLISH_ADMIN_EMAIL` | secret, optional | administrator that publishes the build to the in-app update feed | the admin account's email |
| `CLIENT_PUBLISH_ADMIN_PASSWORD` | secret, optional | that account's password | the password you chose |

The keystore and the public key are produced in
[Local prerequisites](#local-prerequisites-keystore-and-public-key) below.

### Set them with the GitHub CLI

```bash
# 1. Keystore, from the checkout that holds upload.jks
base64 -w0 upload.jks > keystore.b64        # macOS: base64 -i upload.jks -o keystore.b64
gh secret set ANDROID_KEYSTORE_BASE64 < keystore.b64
rm keystore.b64

# 2. The other secrets
gh secret set ANDROID_KEYSTORE_PASSWORD --body '<keystore password>'
gh secret set ANDROID_KEY_ALIAS --body upload
gh secret set ANDROID_KEY_PASSWORD --body '<key password>'

# 3. The two public variables
gh variable set CLIENT_CONTROLLER_URL --body 'https://api.example.com'
gh variable set CLIENT_SIGNING_PUBLIC_KEY \
  --body "$(openssl pkey -in signing-key.pem -pubout -outform DER | tail -c 32 | base64)"

# 4. Optional: let CI publish each build to installed apps
gh secret set CLIENT_PUBLISH_ADMIN_EMAIL --body 'admin@example.com'
gh secret set CLIENT_PUBLISH_ADMIN_PASSWORD --body '<that account password>'
```

`gh` must be authenticated as an account with admin access to the repository:
GitHub returns `HTTP 403: Resource not accessible by integration` for tokens
without it.

### Or in one command

`apps/client/tool/setup-release-secrets.sh` creates the keystore when it is
missing and sets all six values:

```bash
STRICT_CONTROLLER_URL=https://api.example.com \
  ./apps/client/tool/setup-release-secrets.sh
```

It needs the controller's `signing-key.pem`; only the public half is uploaded.
`DRY_RUN=1` prints what it would change without calling `gh`.

### Verify it works

```bash
gh workflow run client            # build now, without an empty commit
gh run watch                     # follow that run
gh run download <run-id> -n strict-proxy-client-android-<commit-sha>
```

The job now asserts what it publishes: the APK's application id, launcher label
and packaged `libbox.so`, plus its signature via `apksigner`. If any value is
wrong or missing the run fails before uploading, so a green run means the
artifact is installable.

Changing `CLIENT_CONTROLLER_URL` or `CLIENT_SIGNING_PUBLIC_KEY` requires a new
build: both are compiled into the app.

### When a value is missing

The Android job stops at **Require release configuration** with the exact list:

```text
error: the Android artifact needs a signed release build, but its configuration is incomplete.
missing:
  - secret ANDROID_KEYSTORE_BASE64
  - variable CLIENT_SIGNING_PUBLIC_KEY
```

Add the named values and re-run (`gh workflow run client`). There is no debug
fallback on purpose: a debug-signed APK installs, but Android would then reject
every future update signed with the real key.

## Local prerequisites (keystore and public key)

### 1. Create the release keystore

Do this once, on a machine you control:

```bash
keytool -genkeypair -v \
  -keystore upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias upload
```

Back up `upload.jks` **and** its passwords. If you lose them, every installed
app can only be updated by uninstalling it first — Android will refuse an APK
signed by a different key.

### 2. Upload them to GitHub

All four secrets and both variables are described in
[GitHub configuration](#github-configuration-required-for-artifacts), together
with the exact commands, the on-demand build, and the failure the workflow
reports when something is missing. Do that before the next push that changes the
client: the Android artifact job fails rather than uploading an unsigned APK.

### 3. Collect the two public build inputs

Two values are left: `CLIENT_CONTROLLER_URL` (your `https://` deployment) and
`CLIENT_SIGNING_PUBLIC_KEY`. The second one causes most of the confusion, so to
be explicit:

- `upload.jks` is the **Android keystore**. It signs the APK. Nothing to do with
  this step.
- `signing-key.pem` is the **controller's Ed25519 key**. The controller signs
  config bundles with it; the client verifies them with its public half. It was
  created when you deployed the controller (`SETUP.md` step 3, or
  [DOKPLOY.md](DOKPLOY.md) step 2).

Pick the case that matches your setup — all three print the same 44-character
base64 string, which is what `CLIENT_SIGNING_PUBLIC_KEY` holds:

```bash
# A. The PEM file is on this machine (you generated it here):
openssl pkey -in signing-key.pem -pubout -outform DER | tail -c 32 | base64

# B. The key only exists as SIGNING_PRIVATE_KEY_PEM in the controller's
#    environment (Dokploy/Compose), with \n escapes. Paste that value:
SIGNING_PRIVATE_KEY_PEM='-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n' \
node -e '
  const { createPublicKey } = require("node:crypto");
  const pem = process.env.SIGNING_PRIVATE_KEY_PEM.replace(/\\n/g, "\n");
  const der = createPublicKey(pem).export({ type: "spki", format: "der" });
  process.stdout.write(der.subarray(-32).toString("base64") + "\n");
'

# C. You have the PEM public key (e.g. what `npm run db:seed` prints):
openssl pkey -pubin -in public.pem -outform DER | tail -c 32 | base64
```

If you generated the secrets with `scripts/generate-secrets.sh` (`SETUP.md`
step 3), the `STRICT_SIGNING_PUBLIC_KEY=` line in its `secrets.txt` is already
this value — copy it, no derivation needed.

A correct value decodes to exactly 32 bytes and looks like
`6w1/gYyMvdBS2dFbcSq3TUmt8KqYfvFBTZ0jLkaBAGM=`. The workflow rejects anything
else at the configuration gate.

> **Do not invent a key here.** If the controller is already running, it must be
> the key in its `SIGNING_PRIVATE_KEY_PEM`. Building the client with a different
> public key makes every bundle fail verification ("tampered configuration"),
> and the fix is a rebuild for every user. Rotating the key is a separate,
> deliberate operation (`README.md` → Signing keys).

The sing-box commit the VPN engine is built from is pinned in
`apps/client/libbox.ref` as a full 40-character SHA, so neither CI nor a local
build needs you to supply one. Upgrading the engine means reviewing the upstream
diff, replacing that SHA, and rebuilding — never pointing it at a branch.

## Run a release

The workflow builds `libbox.aar` for the two Android ABIs it publishes
(`android/arm64`, `android/arm`; Go 1.25.5 on the runner, matching the pinned
engine's `go.mod`), compiles **one APK per ABI** (`--split-per-abi`), re-signs
each with your keystore, verifies the signature and the packaged engine, and
uploads the artifacts. Expect roughly 15–25 minutes on a cold cache because of
the native build.

x86/x86_64 are emulator-only and are neither built nor published, which removes
a third of the engine binding, packaging and signature work. A local build still
covers all four by default: set `LIBBOX_ANDROID_PLATFORMS` and
`TARGET_PLATFORMS` if you need an emulator build.

Each release's notes list the client commits since the previous `client-*` tag,
so a published build number can be traced to the changes it contains.

```bash
gh workflow run client-release \
  -f controller_url=https://api.example.com \
  -f signing_public_key='<base64 key from step 3>' \
  -f signing_key_id=primary \
  -f app_version=0.1.0 \
  -f app_build_number=1 \
  -f release_tag=v0.1.0        # optional: attaches the APK to a GitHub release
```

`libbox_ref` is optional: leave it out to use the commit pinned in
`apps/client/libbox.ref`, or pass a full SHA for a one-off engine build.

Leaving `release_tag` empty still uploads the APK as a workflow artifact; you can
download it from the run page.

## Local build (same result)

With Flutter, Go 1.22 or 1.23, the Android SDK with an NDK, and `zip` installed
(`tool/build-libbox.sh` installs the matching `gomobile` itself):

```bash
export STRICT_CONTROLLER_URL=https://api.example.com
export STRICT_SIGNING_PUBLIC_KEY='<base64 public key>'
export APP_VERSION=0.1.0 APP_BUILD_NUMBER=1
# Optional: defaults to the pinned commit in apps/client/libbox.ref
export SING_BOX_LIBBOX_REF=<40-character SHA>

export ANDROID_KEYSTORE_PATH="$PWD/upload.jks"
export ANDROID_KEYSTORE_PASSWORD='...'
export ANDROID_KEY_ALIAS=upload
export ANDROID_KEY_PASSWORD='...'   # omit if same as keystore password

./apps/client/tool/build-release-android.sh
```

The artifacts land in `apps/client/build/dist/`, one per ABI
(`strict-proxy-0.2.0-20-arm64-v8a.apk`, `…-armeabi-v7a.apk`).
Set `SPLIT_ABI=0` for a single universal APK. `TARGET_PLATFORMS` narrows the ABI
set: the release workflow uses `android-arm,android-arm64`, and adding
`android-x64` builds an emulator APK on demand. The script ends by asserting each
APK's application id, launcher label, and a packaged `libbox.so` for every ABI it
contains, so a build with the placeholder id or without the engine fails instead
of being handed over (`tool/verify-android-apk.sh`; CI runs the same check).

## Distributing to users

- **Direct install:** host the APK over HTTPS and give users the link. They must
  allow installs from the browser/file manager once. `adb install -r <apk>` works
  for testing; give each device the APK for its ABI (`arm64-v8a` for a modern
  phone, `armeabi-v7a` for an older one).
- **GitHub Releases:** every push to `main` that builds the client publishes a
  release tagged `client-<run_number>` with the signed APK and the Linux bundle
  (`gh release list`, newest first). `client-release`'s `release_tag` input
  publishes a versioned release the same way, which is the right choice for a
  named version; both are shareable links.

  Run artifacts expire after their retention window, so the release is the copy
  to keep. The APK filename includes the commit, and the build number
  (the workflow run number) increases with every build, so Android accepts the
  newest one as an update.
- **Play Store:** requires a Play Console account and an `.aab`. The Play upload
  key is managed by Google Play App Signing; direct-APK updates and Play updates
  are separate tracks, so pick one and stay on it.

### Updates

Bump `app_build_number` for every release — Android compares the version code.
Build with the same keystore, or the install will be rejected as a signature
mismatch. Because the signing key is compiled into the app, changing
`STRICT_SIGNING_PUBLIC_KEY` also requires a new build for every user.

### In-app updates

Installed apps find and install new builds themselves: at launch the app asks
the controller whether a newer build exists, and offers an update that downloads
the APK and opens Android's package installer. The app is replaced in place and
keeps its data and session. Android still shows one confirmation and refuses an
APK signed with a different key, so keep using the same release keystore.

#### Publish from the dashboard

Open **Admin → Client apps**. For each ABI you built, upload the APK with the
version name, an increasing build number and the release notes; then publish.
Publishing is a separate action from uploading, so a release with only one of
three ABIs uploaded is stored as a **draft** until you say it is ready. The
screen also lets you withdraw a build (users keep running it, but it stops being
offered) and delete one (its APKs are removed from disk).

The highest **published** build is what `GET /api/v1/app/android` reports. The
app compares that build number with the one compiled into it (`APP_BUILD_NUMBER`,
passed as both `--build-number` and a dart-define), so a build number must
always increase — never reuse one, and never publish a lower number to roll back;
Android refuses to downgrade. To roll back, publish a *new* build whose code is
older.

Uploads are stored under `CLIENT_ANDROID_STORAGE_DIR` (default
`var/client-releases`; Compose and Dokploy mount
`/var/lib/strict-proxy/client-releases` on a named volume). Keep it on persistent
storage, or a redeploy deletes the APKs apps are being offered.

#### Publishing from a release pipeline

`apps/client/tool/publish-android-release.sh` does the same thing without a
browser: sign in as an administrator, upload every APK in `build/dist` under one
build number, publish, then download the result back and compare SHA-256.

```bash
APP_VERSION=0.2.0 APP_BUILD_NUMBER=20 \
CONTROLLER_URL=https://strictproxy.devlouix.com \
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD='...' \
  ./apps/client/tool/publish-android-release.sh
```

`PUBLISH=0` uploads a draft instead. The script fails if the feed does not end up
offering the build it just uploaded, so a green run means installed apps can
actually update.

The `client` workflow does this for you: after attaching the APKs to the GitHub
release it runs the same script against `dist-android`, using
`CLIENT_PUBLISH_ADMIN_EMAIL` / `CLIENT_PUBLISH_ADMIN_PASSWORD` and the build
number from the run. A GitHub release on its own is not reachable by the
updater — only a published catalog entry is.

#### What the app downloads

`GET /api/v1/app/android` returns the version, build number, notes and one entry
per published ABI; `GET /api/v1/app/android/download?abi=<abi>` serves that
exact APK. Both are unauthenticated — the APK is public, and its signature is
what makes Android accept it — and both answer 404 when nothing is published.
The app reads `Build.SUPPORTED_ABIS`, asks for its own ABI, and falls back to a
`universal` APK. A release that has no APK for the device's ABI is refused with
`CLIENT_ABI_UNAVAILABLE` rather than given a binary its CPU cannot run.

#### Older deployments: environment configuration

A deployment that predates the dashboard can still publish a single APK with
`CLIENT_ANDROID_VERSION`, `CLIENT_ANDROID_BUILD_NUMBER`,
`CLIENT_ANDROID_APK_PATH` (inside the controller container) and
`CLIENT_ANDROID_NOTES`. It is served as a `universal` artifact, and the first
build published from **Client apps** takes precedence over it.

#### Requiring a minimum build

An operator can retire old APKs without touching the node fleet: **Settings →
Client version** in the admin dashboard sets the lowest build number allowed to
connect. `0` or a blank field disables the gate (the default).

The app sends `x-client-build` (its `APP_BUILD_NUMBER`) on every request. When
the caller is older, `GET /api/v1/network/config` answers:

```json
{ "code": "CLIENT_UPDATE_REQUIRED", "error": "…build 67 or newer.", "minimumBuild": 67 }
```

with HTTP `426`. No tunnel credentials are issued, so the old build cannot carry
traffic even if it is already signed in. The app turns that into an update
prompt through the in-app updater — the same feed as any other update — rather
than a bare "connection failed".

The value is stored as `client.minBuild` in `platform_settings` and written with
`PUT /api/v1/admin/settings/client` (`{"minimumBuild": 67}`, or `0` to clear).

Two operational rules:

- **Set it to a build that exists.** Raise the minimum only after the new APK is
  published and installable; otherwise users are blocked with nothing to install.
- **Builds older than this check send no header and are refused.** That is the
  point of the gate, but it means enabling it immediately blocks every install
  that predates the feature. Set the minimum to the first build people can
  update to.

#### Crash reports

The app posts uncaught Flutter and platform errors to
`POST /api/v1/client/crashes` — unauthenticated, rate limited, truncated and
deduplicated by a client-generated id. **Client apps** lists the most recent
reports with build, ABI, device and stack trace, which is how a crash on a phone
becomes diagnosable without `adb logcat`.

## iOS

The workflow does not produce iOS builds. iOS needs an Apple Developer account,
a distribution certificate and provisioning profiles, plus the Packet Tunnel
extension target described in [apps/client/LIBBOX.md](../apps/client/LIBBOX.md).
CI compiles iOS with `--no-codesign` to catch breakage, but only when the
repository variable `ENABLE_IOS_VERIFICATION=true` — GitHub only provides macOS
runners on plans that include them, and an unprovisioned job fails before it can
report anything useful. A shippable iOS build is a manual Xcode step.

## Pre-release check

Before sharing a build:

1. Install it on a real device, not just an emulator.
2. Log in, open the server list, and connect — this exercises the signed bundle,
   the libbox engine, and VPN permission end to end.
3. Confirm the About/Connection screen shows the expected controller URL (never
   `10.0.2.2`).
4. Make a test purchase if billing is enabled; the tier must change after the
   webhook, not after the redirect.
