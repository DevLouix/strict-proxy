# Releasing the Android client

This is how an installable, connectable APK is produced. The `client` workflow
runs on every push: it builds the native `libbox.aar` from the pinned commit,
applies the real Android identity, and uploads an APK. Once the release secrets
and variables below exist, that push artifact is a **signed release** build;
without them it is a debug APK for testing only, never for users. The
`client-release` workflow runs the same chain with no fallback, plus an optional
GitHub release — use it when you want a specific version number or tag.

## What the release build guarantees

`apps/client/tool/build-release-android.sh` refuses to produce an artifact
unless all of the following hold:

| Requirement | Why |
|---|---|
| `STRICT_ENV=production` | unsigned config bundles are rejected instead of silently trusted |
| `STRICT_CONTROLLER_URL` starts with `https://` | credentials never travel over cleartext |
| `STRICT_SIGNING_PUBLIC_KEY` is set | the client verifies the controller's Ed25519 signature; a missing key is a hard failure |
| `libbox.aar` exists | without the native engine the app installs but cannot open a VPN session. Built automatically from the sha in `apps/client/libbox.ref` |
| A real keystore is supplied | the APK is re-signed, so future builds can update it in place |

### Android identity

`apps/client/android/` is generated by `flutter create` on every clean checkout,
so the installed package id, code namespace and launcher label are applied by
`apps/client/tool/configure-android-host.sh` rather than edited by hand. Defaults:
`com.strictproxy.client` and the label `StrictProxy`; override them with
`STRICT_ANDROID_APP_ID` and `STRICT_ANDROID_APP_LABEL`. Keep the id stable after
the first release — a new id installs as a different app instead of updating.

## One-time setup

### 1. Create the release keystore

Do this once, on a machine you control:

```bash
keytool -genkeypair -v \
  -keystore upload.jks \
  -keyalg RSA -keysize 2048 -validity 10000 \
  -alias upload
```

Back up `upload.jks` **and** its passwords. If you lose them, every installed
app can only be updated by uninstalling it first — Android will refuse an APK
signed by a different key.

### 2. Add the GitHub secrets

Repository **Settings → Secrets and variables → Actions**:

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 upload.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | keystore password |
| `ANDROID_KEY_ALIAS` | `upload` |
| `ANDROID_KEY_PASSWORD` | key password (often the same) |

Both workflows use them: `client-release` always builds signed, while `client`
uses them for the push artifact whenever they exist and falls back to a debug APK
when they do not.

#### Or set all six at once

From a checkout that has the controller's `signing-key.pem` and `gh` logged in:

```bash
STRICT_CONTROLLER_URL=https://api.example.com \
  ./apps/client/tool/setup-release-secrets.sh
```

It generates `upload.jks` when absent (password written to `upload.jks.password`),
derives the public key from the private one, and sets the four secrets plus
`CLIENT_CONTROLLER_URL` and `CLIENT_SIGNING_PUBLIC_KEY`. `DRY_RUN=1` prints what it
would change without calling `gh`, and only the public key is uploaded — the
private key never leaves the machine.

### 3. Collect the two public build inputs

```bash
# From the controller's signing key (NOT a secret — it only verifies):
openssl pkey -in signing-key.pem -pubout -outform DER | tail -c 32 | base64
```

The `sing-box-libbox` commit the VPN engine is built from is pinned in
`apps/client/libbox.ref` as a full 40-character SHA, so neither CI nor a local
build needs you to supply one. Upgrading the engine means reviewing the upstream
diff, replacing that SHA, and rebuilding — never pointing it at a branch.

## Run a release

The workflow builds `libbox.aar` for all four Android ABIs (Go 1.22 on the
runner: the pinned gomobile does not compile on Go 1.24+), compiles the APK,
re-signs it with your keystore, verifies the signature, and uploads the artifact.
Expect roughly 15–25 minutes on a cold cache because of the native build.

```bash
gh workflow run client-release \
  -f controller_url=https://api.example.com \
  -f signing_public_key='<base64 key from step 3>' \
  -f signing_key_id=primary \
  -f app_version=0.1.0 \
  -f app_build_number=1 \
  -f release_tag=v0.1.0        # optional: attaches the APK to a GitHub release
```

`libbox_ref` is optional: leave it out to use the commit pinned in
`apps/client/libbox.ref`, or pass a full SHA for a one-off engine build.

Leaving `release_tag` empty still uploads the APK as a workflow artifact; you can
download it from the run page.

## Local build (same result)

With Flutter, Go 1.22 or 1.23, the Android SDK with an NDK, and `zip` installed
(`tool/build-libbox.sh` installs the matching `gomobile` itself):

```bash
export STRICT_CONTROLLER_URL=https://api.example.com
export STRICT_SIGNING_PUBLIC_KEY='<base64 public key>'
export APP_VERSION=0.1.0 APP_BUILD_NUMBER=1
# Optional: defaults to the pinned commit in apps/client/libbox.ref
export SING_BOX_LIBBOX_REF=<40-character SHA>

export ANDROID_KEYSTORE_PATH="$PWD/upload.jks"
export ANDROID_KEYSTORE_PASSWORD='...'
export ANDROID_KEY_ALIAS=upload
export ANDROID_KEY_PASSWORD='...'   # omit if same as keystore password

./apps/client/tool/build-release-android.sh
```

The artifact lands in `apps/client/build/dist/`. The script ends by asserting the
APK's application id, launcher label, and packaged `libbox.so`, so a build with
the placeholder id or without the engine fails instead of being handed over
(`tool/verify-android-apk.sh`; CI runs the same check on the push artifact).

## Distributing to users

- **Direct install:** host the APK over HTTPS and give users the link. They must
  allow installs from the browser/file manager once. `adb install -r <apk>` works
  for testing.
- **GitHub Releases:** the workflow's `release_tag` input publishes the APK on a
  release page, which is the simplest shareable location.
- **Play Store:** requires a Play Console account and an `.aab`. The Play upload
  key is managed by Google Play App Signing; direct-APK updates and Play updates
  are separate tracks, so pick one and stay on it.

### Updates

Bump `app_build_number` for every release — Android compares the version code.
Build with the same keystore, or the install will be rejected as a signature
mismatch. Because the signing key is compiled into the app, changing
`STRICT_SIGNING_PUBLIC_KEY` also requires a new build for every user.

## iOS

The workflow does not produce iOS builds. iOS needs an Apple Developer account,
a distribution certificate and provisioning profiles, plus the Packet Tunnel
extension target described in [apps/client/LIBBOX.md](../apps/client/LIBBOX.md).
CI compiles iOS with `--no-codesign` to catch breakage, but only when the
repository variable `ENABLE_IOS_VERIFICATION=true` — GitHub only provides macOS
runners on plans that include them, and an unprovisioned job fails before it can
report anything useful. A shippable iOS build is a manual Xcode step.

## Pre-release check

Before sharing a build:

1. Install it on a real device, not just an emulator.
2. Log in, open the server list, and connect — this exercises the signed bundle,
   the libbox engine, and VPN permission end to end.
3. Confirm the About/Connection screen shows the expected controller URL (never
   `10.0.2.2`).
4. Make a test purchase if billing is enabled; the tier must change after the
   webhook, not after the redirect.
