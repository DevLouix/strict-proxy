# Building and testing the client locally

This page is written for an agent (or a person) that has to get the Flutter client
building, run its tests, and prove a change works **without** GitHub Actions and
without a real phone. Every command here was run on a Linux host; nothing needs
credentials, Docker, or network access beyond package downloads (and the native
engine clone).

The client lives in [`apps/client`](../apps/client). Sections 1–3 are the minimum
loop; 4–7 are for when you need to actually connect.

> **Never** put a credential in `--dart-define`: binaries are inspectable, and CI
> already builds every artifact with public values only.

## 1. Prerequisites

| Tool | Version | Notes |
|---|---|---|
| Flutter | **3.47.9** | CI's pin. 3.50.0 passes `analyze` and `test` but its *release* APK build dies inside Android lint (`JavaDocParser.parseDataItem NoSuchMethodError` while linting `url_launcher_android`). |
| Go | **1.25.5** | Must satisfy the engine's `go.mod` (`go 1.25.5` for sing-box v1.14.4). A newer global Go is fine only if `GOTOOLCHAIN` is allowed to fetch; CI's `GOTOOLCHAIN=local` is not. |
| Android SDK | build-tools, `platforms;android-35`, **NDK ≥ 28** | NDK 27 fails the engine link with `unknown relocation (315)` in `libcronet.a`. CI uses `28.0.13004108`; `setup-linux.sh` installs `28.2.13676358`. Both work. |
| JDK | 17 | Gradle and AGP. |
| `zip`, `unzip` | any | APK re-signing and verification. |
| Linux desktop deps | `clang cmake ninja-build pkg-config libgtk-3-dev liblzma-dev libsecret-1-dev` | `libsecret-1-dev` is required by `flutter_secure_storage_linux`, else the Linux build fails during CMake configure. |

Two environment traps that cost real time:

- **A different global `GOROOT` breaks the engine build.** If `go env GOROOT`
  points at, say, `/usr/local/go` from a newer release, run the engine build with
  `unset GOROOT` and `GOTOOLCHAIN=local`, or install 1.25.5 and put it first on
  `PATH`.
- **Disk.** The engine build (sing-box + cronet + tailscale, four ABIs) plus
  Gradle intermediates needs well over 10 GB. Check `df -h` first. A workspace on
  a 32 GB loop device is not enough — build from a copy under `/tmp` in that case
  and keep `GRADLE_USER_HOME`, the AAR and the Android SDK there.

`./apps/client/tool/setup-linux.sh` installs the Debian/Ubuntu packages, Flutter
and the Android SDK, then runs the tests once, if you want the whole environment
in one step.

## 2. Generate the host projects (required, every clean checkout)

`apps/client/android/`, `ios/` and `linux/` are generated by `flutter create` and
are not committed, so the real package id, launcher label, ProGuard rules, updater
manifest and `MainActivity` are applied by a script:

```bash
cd apps/client
flutter create --platforms=linux,android .
./tool/configure-android-host.sh
flutter pub get
```

Skipping `configure-android-host.sh` gives you an APK with the `com.example.*`
placeholder that cannot be published or updated — `tool/verify-android-apk.sh`
fails on it later and the cause is not obvious.

## 3. The fast loop: tests and analysis

No device, no TUN, no root, no controller:

```bash
cd apps/client
flutter test        # 14 suites: widgets, verification, config, recovery, Linux engine
flutter analyze     # must be clean; do not add ignore comments to make it pass
```

`flutter test` must run **from `apps/client`**: `test/canonical_fixtures.json` is
loaded by path at runtime. `flutter analyze` fails on any `package:flutter/material`
deprecation on a newer Flutter, which is one of the reasons the version is pinned.

The Android bridge is Kotlin, so only Gradle can compile it. It needs the unpacked
engine classes from section 4 first:

```bash
cd apps/client
flutter build apk --debug --config-only        # writes Gradle files, no APK
cd android && ./gradlew :strict_proxy_libbox_bridge:testDebugUnitTest --no-daemon
```

`TunPlanTest` covers the pure-Kotlin TUN rules and `EngineLogTest` the buffer
behind the Diagnostics tunnel log; this step also compiles `LibboxVpnService`
and `LibboxPlatformInterface`, which is what fails when the engine's generated
API changes. Without `libbox-classes.jar` the module cannot
compile at all (`checkLibboxClasses` says so in one line).

CI runs exactly the four commands above plus `bash -n` over `apps/client/tool/*.sh`
and `tool/check-android-libbox.sh`. To reproduce a red `verify` job locally, run
those.

## 4. Build the native engine (`libbox.aar`)

Compilation does not need the engine; **connecting** does. It is built from the
commit pinned in [`apps/client/libbox.ref`](../apps/client/libbox.ref) — never a
tag or branch:

```bash
# all four ABIs (arm64, arm, 386, amd64) — what a dev box wants, incl. emulator
./apps/client/tool/build-libbox.sh --android-only

# release/CI shape: only the ABIs that get published
LIBBOX_ANDROID_PLATFORMS=android/arm64,android/arm \
  ./apps/client/tool/build-libbox.sh --android-only
```

Expect 15–25 minutes cold. The script clones `SagerNet/sing-box` into
`apps/client/.cache/sing-box-libbox` (override with `SING_BOX_LIBBOX_WORK_DIR`),
installs the exact `github.com/sagernet/gomobile` its `go.mod` pins (never
`gobind@latest`), resolves `ANDROID_NDK_HOME` from `ANDROID_SDK_ROOT`/`ANDROID_HOME`
when unset, and writes:

- `packages/libbox_bridge/android/libs/libbox.aar`
- `libbox-classes.jar` + `libs/<abi>/libbox.so` (the AAR expanded for Gradle — AGP
  refuses a local `.aar` inside a library module)
- `packages/libbox_bridge/ios/Frameworks/Libbox.xcframework` (skipped by
  `--android-only`; needs Xcode)

Useful caches on a slow or small host:

```bash
export GOPATH=/tmp/gopath GOCACHE=/tmp/gocache GOPATH_BIN=/tmp/gopath/bin
export SING_BOX_LIBBOX_WORK_DIR=/tmp/singbox-work
export ANDROID_HOME=/tmp/and/sdk ANDROID_SDK_ROOT=/tmp/and/sdk
export GRADLE_USER_HOME=/tmp/gradle-home
```

Sanity-check a rebuilt AAR (this is the failure mode that reaches a phone as
"connected" then immediately drops):

```bash
unzip -l apps/client/packages/libbox_bridge/android/libs/libbox.aar | grep 'jni/'
unzip -p apps/client/packages/libbox_bridge/android/libs/libbox.aar classes.jar > /tmp/c.jar
unzip -l /tmp/c.jar | grep 'io/nekohasekai/libbox/OverrideOptions.class'
```

Every ABI in the AAR must carry `libbox.so`, and `OverrideOptions` must exist —
`packages/libbox_bridge/android/build.gradle` rejects an engine without it.

## 5. Build the app

### Linux desktop (fastest end-to-end check)

```bash
cd apps/client
flutter build linux --release \
  --dart-define=STRICT_ENV=development \
  --dart-define=STRICT_CONTROLLER_URL=http://127.0.0.1:8080
./build/linux/x64/release/bundle/strict_proxy_client
```

The Linux engine shells out to an installed `sing-box`; point at it with
`STRICT_SING_BOX_BIN=/absolute/path/to/sing-box`. Opening a TUN needs the
privileges the inbound config asks for.

### Android debug APK for an emulator or device

```bash
cd apps/client
flutter build apk --debug \
  --dart-define=STRICT_ENV=development \
  --dart-define=STRICT_CONTROLLER_URL=http://10.0.2.2:8080   # emulator -> host
adb install -r build/app/outputs/flutter-apk/app-debug.apk
```

`10.0.2.2` is the host from inside the emulator. On a physical device the
controller must be reachable on the LAN, or use a production HTTPS URL.

An emulator is `x86_64`, so its APK **and** engine must include that ABI:

```bash
LIBBOX_ANDROID_PLATFORMS=android/amd64 ./apps/client/tool/build-libbox.sh --android-only
cd apps/client && flutter build apk --release --target-platform android-x64 ...
```

An ARM-only engine installed on an x86_64 emulator fails at login/connect with
`SIGILL` — that is a translation artifact, not a code bug.

### Signed release APK (the shape users get)

```bash
export STRICT_CONTROLLER_URL=https://api.example.com
export STRICT_SIGNING_PUBLIC_KEY='<base64 of the controller Ed25519 PUBLIC key>'
export APP_VERSION=0.1.0 APP_BUILD_NUMBER=42
export ANDROID_KEYSTORE_PATH="$PWD/upload.jks" ANDROID_KEYSTORE_PASSWORD=... ANDROID_KEY_ALIAS=upload

SKIP_LIBBOX=1 TARGET_PLATFORMS=android-arm,android-arm64 \
  ./apps/client/tool/build-release-android.sh
```

It refuses to emit an APK unless the URL is HTTPS, the public key is present,
`libbox.aar` exists, and every APK then passes `tool/verify-android-apk.sh`
(application id, launcher label, `libbox.so` for each ABI present) and
`apksigner`. Output goes to `apps/client/build/dist/`, one APK per ABI.
`SKIP_LIBBOX=1` reuses an existing AAR; omit it to rebuild the engine first.

Keystore setup, variables and the GitHub side are in
[RELEASE-CLIENT.md](RELEASE-CLIENT.md); you do not need any of them to test.

## 6. Test against a local controller

Login, the server list and the signed config bundle all need a controller. Local
stack (from the repository root):

```bash
docker compose up -d postgres redis
npm install
npx tsx apps/controller/src/scripts/generate-env.ts   # writes .env
set -a; source .env; set +a
npm run db:migrate -w apps/controller
npm run db:seed -w apps/controller                    # prints the admin password
npm run dev:controller                                # http://localhost:8080
```

`GET /api/v1/network/config` needs an **active subscription** and a node, so a
fresh account sees no servers until the seed's development node is online (or a
node is enrolled). Use a `standard`/`pro` account for a connect test — `free` has
no tunnel access by design.

For a development build `STRICT_ENV=development` accepts an unsigned bundle; it
still needs a reachable controller URL. `STRICT_ENV=production` makes bundle
verification mandatory and is what release builds use.

## 7. Verifying an actual tunnel

```bash
adb logcat -c && adb logcat | grep -Ev '^(D|I)/'      # noise off, then connect in the UI
adb shell ip addr show tun0                          # e.g. 172.19.0.1/30
adb shell pidof com.strictproxy.client
```

What a working session looks like: VPN consent once, the home screen reaches
`Connected · <region>`, the app pid stays stable, `tun0` exists, and there is no
`E/Go: panic` in logcat. A native crash appears as
`F/libc: Fatal signal 6 (SIGABRT)` immediately after an `E/Go: panic:` line —
that is the engine, not Dart, and the app's diagnostics screen ("Last engine
exit") carries the tail of it.

To prove a specific Dart/Kotlin change reached a built APK without installing it:

```bash
unzip -p <apk> classes.dex | strings | grep -c <symbol-you-changed>   # expect > 0
unzip -p <apk> lib/arm64-v8a/libbox.so > /dev/null && echo engine-present
unzip -p <apk> META-INF/UPLOAD.RSA | openssl pkcs7 -inform DER -print_certs \
  | openssl x509 -noout -subject -fingerprint -sha256                  # signing identity
```

`tool/verify-android-apk.sh <apk>` does the id/label/engine checks for you; the
signature fingerprint must match the release keystore or Android will refuse to
update an installed copy. Note that one APK can differ in content and still have
the same byte size as another, so compare a `md5sum` of `classes.dex`, not `ls -l`.

## 8. Traps that already cost someone an afternoon

| Symptom | Cause | Fix |
|---|---|---|
| `unknown relocation (315)` while linking `libcronet.a` | NDK 27 | install NDK ≥ 28, export `ANDROID_NDK_HOME` |
| `could not build gomobile …; … requires Go 1.25.5 but this is go1.27.1` | wrong Go | install/pin 1.25.5; `unset GOROOT`; `GOTOOLCHAIN=local` |
| Gradle/AGP dies mid-build, `No space left on device` | engine + Gradle on one small volume | build under `/tmp`, `GRADLE_USER_HOME` there, remove `.cache/sing-box-libbox` after |
| `Direct local .aar file dependencies are not supported` | AGP limitation | run `tool/unpack-libbox-aar.sh` (the build scripts already do) |
| APK installs, cannot open a VPN session | engine not bundled | `tool/build-libbox.sh`, then `tool/verify-android-apk.sh` |
| `SIGILL` at login on an emulator | ARM-only engine on x86_64 | rebuild with `android/amd64` |
| Linux build fails in CMake on `libsecret` | missing `libsecret-1-dev` | install it |
| `flutter analyze` fails on untouched files | unpinned/newer Flutter | use 3.47.9 |
| app cannot log in from an emulator | `STRICT_CONTROLLER_URL` is `localhost` | `http://10.0.2.2:8080` |

## 9. Rules a change must not break

- Generated host projects, `libbox.aar`, `.cache/` and `build/` stay out of git.
- No lint/analyzer suppressions and no skipped or weakened tests to make CI green.
- The engine pin stays a full 40-character SHA; upgrading it is a reviewed
  dependency change ([LIBBOX.md](../apps/client/LIBBOX.md) → Upgrading the
  engine), and the node image's `SING_BOX_VERSION` moves with it.
- Adding a shipped ABI means changing both `LIBBOX_ANDROID_PLATFORMS` and
  `TARGET_PLATFORMS`, or the APK ships without an engine for that CPU.
- The CI equivalent of everything above is `.github/workflows/client.yml`; if you
  change a build step there, mirror it here.
